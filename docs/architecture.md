# Architecture and safety

`model.ts` validates persisted task/settings shapes and durable wall-clock timers. `codec.ts` recognizes actual Markdown tasks and preserves IDs, markers, indentation and history. `repository.ts` is the file/Editor boundary. `daily.ts` owns date/path recognition. `timeline.ts` turns recorded work sessions into per-day blocks for the Week/Day views. `service.ts` serializes explicit actions, recurrence, historical propagation, forwarding and undo. `main.ts` registers lifecycle and user syntax; `render.ts` is read-only. `view.ts`, `modals.ts`, `settings.ts` use host UI.

Records are ordinary Markdown files in `Tasks/`, named after the todo's title (`Tasks/Plan the launch.md`, `Plan the launch 2.md` for a duplicate; older notes are still named `Tasks/<id>.md`). A record is identified by the `id` in its frontmatter: `Repository` keeps an id to file lookup (built from the notes' text, kept current by create, rename, delete and modify events, never from the lagging metadata cache), so a note can be renamed by hand without breaking its todos. If two notes claim one id (for example a copy), neither is read, listed or changed until one is removed, and the error names both. Occurrences carry `<!--organized:<id>-->`; recurring generated lines also carry `<!--organized:repeat-->`. Copying an ID means the same task. Use **Duplicate as new task** for an independent record. Removing a line never deletes a task file; **Delete task** confirms before trashing the canonical note and removing occurrences. Optional task retention (disabled at 0 days) stamps completion/cancellation dates, unlinks expired completed/canceled occurrences into regular checkboxes, then moves canonical notes to Obsidian's trash during today's daily-note reconciliation. Open/in-progress and recurring tasks are excluded; legacy closed records without a trustworthy transition date are preserved. A failed/conflicting reference update preserves the canonical note. Missing/invalid records require explicit repair. **Convert unchecked todos to tasks** is also explicit: it confirms first, creates canonical notes for unlinked unchecked todos only, and rewrites the source lines once while preserving indentation and line endings. Completed, in-progress, linked and empty todos are left untouched.

Task recognition uses a real Lezer Markdown tree, excludes YAML, fenced/indented code (including nested list fences), HTML/comments and quotes, and recognizes ATX/setext headings. A bounded four-document parse cache avoids reparsing the same editor text on cursor/viewport changes. The parser and its two dependencies are exact-pinned and bundled together, isolated from host parser versions; their MIT notices ship inside main.js. CodeMirror state/view remain host-external with Obsidian's exact peer pins.

## Deliberate compatibility corrections to the original plan

- The default storage folder is **Tasks**, not `.tasks`. Obsidian does not index dot-prefixed folders through Vault/FileManager; a hidden default would make tasks inaccessible to the native frontmatter API and ordinary Markdown editing. Hidden task storage is rejected rather than silently bypassing the host API. No existing files are moved automatically.
- Core Daily Notes exposes no public configuration getter. Match the custom folder/format to the core plugin. No undocumented internal settings are inspected.
- Minimum app version is 1.7.2 for `workspace.revealLeaf` and deferred views. Classic settings remain usable on older supported builds; modern settings search uses grouped individual row definitions shared with the classic renderer.
- Calendar Plus informed the month grid, adjacent dates and selected/today states; native DOM replaces Svelte. No Calendar Plus implementation was copied.

## Conflict policy

All actions run through a per-plugin serial queue. Background edits compare exact previously read content inside `Vault.process`; active edits compare the Editor buffer and use one minimal transaction. A changed note is preserved and reported. This is optimistic, not a cross-device distributed transaction: sync tools can still replace a file after a successful local write. Keep vault backups and inspect sync conflicts. Multi-file actions may partially succeed; canonical metadata and linked IDs support explicit repair. Task files are never automatically deleted as rollback.

Status propagates only to today/future daily notes and undated references; earlier daily notes stay historical. Recurring dates are independent and the shared record stays open. Titles are canonical across all dates. Generated properties never enter source. References build lazily on first request; the index is disposable.

Inspector focus is not a cursor-context change: an absent active Markdown editor preserves the selected task. Actual editor context changes replace it. Optional inspector cards require populated metadata or an explicitly requested module; references load when expanded. Task titles and the description and sources edit inline rather than in a popup, and Save/Cancel render above the field so an on-screen mobile keyboard cannot cover them. Markdown links in task titles and note sections are routed through the workspace using the canonical task-note source path; the task hero and one grouped details surface reduce visual fragmentation. Description is the canonical heading shown above Idea; legacy `## Information` is read as Description and migrated on save without deleting other sections. Live Preview replacement decorations hide identity/recurrence comments even on the active line and expose atomic cursor ranges; source mode remains unchanged. The task-property widget becomes inline at document EOF because CodeMirror drops a block widget exactly at EOF without a trailing newline.

Crash state and settings snapshots live under the plugin folder, not in vault notes. Newer data pauses writes. Settings restore is queued for next restart; current data is snapshotted before restore. Retention preserves the newest stable-written backup in addition to recent snapshots. Backups cover settings only, not user task/note Markdown. Sync can restore newer data again; coordinate versions across devices before resuming sync.

Explicit task deletion is serialized like every other action. It asks for confirmation, removes every linked occurrence line from Markdown notes outside the task folder, then hands the canonical note to Obsidian's `FileManager.trashFile` so the user's own trash preference applies. The delete is not added to Organized's undo stack: the canonical file lives in the host trash, while removed occurrence lines are recovered from vault history or backups. Retention is separately opt-in; its data-changing pass occurs only while opening today's daily note, after explicit configuration, and converts task lines to ordinary unchecked/checked/canceled todos before trashing task notes. A failure/conflict leaves the canonical task note in place, even if earlier note references were already converted; retry can safely finish remaining references.

Snapshot writes stage to a temporary plugin-local file and rename, falling back to a direct write on adapters without rename/temp support. That fallback has weaker crash guarantees; it never removes an existing target first. Settings restoration uses an exact-content comparison inside adapter.process when available and otherwise the documented staged/direct fallback. Crash-loop detection pauses features for the unsuccessful launch instead of calling Obsidian's undocumented plugin-disable internals; restarting/re-enabling clears its recovery state.

## Task note layout and migration

A task note is `---` YAML properties `---`, then the description as plain text, then an optional `## Sources` heading with links. Nothing else is written, so the note stays readable without Organized. The reader also accepts the older layout (`## Description` or `## Information`, `## Notes`, `## Idea`, `## Question`, `## Sources`): every section is merged into the description and nothing is dropped, and a note is rewritten in the new layout when its description or sources are saved. A heading of the user's own inside a new-layout description (`## Plan`, even `## Notes`) is content.

After updating, one migration (`taskNotesMigrated`, run once after the workspace is ready, never on load) rewrites every task note still in the old layout. Before it writes, the old text of each note it will change is saved to `note-backups/task-notes-<time>.json` in the plugin folder (the three newest are kept; a failed backup means no note is changed). It only touches real task notes (unreadable and newer-schema notes are left alone), writes with the usual compare-and-swap, is idempotent per note, reports what it did with an Undo button, and retries on the next start if any note failed.

A second one-time migration (`taskNoteNamesMigrated`, run right after it) names task notes that are still named after their id after the title of their todo (`migrateTaskNames` in the service). Candidates are valid notes whose file name equals their id, which are not time records of a standalone note (`converted_to`) and whose id is claimed by no other note; they are renamed oldest first (so a duplicate title gets `Plan 2` in a stable order) to names unique across the whole vault. The planned renames are saved to `note-backups/task-names-<time>.json` first (nothing is renamed when that fails); each rename goes through `fileManager.renameFile` so links follow; a note that cannot be renamed keeps its id name and is listed in the notice; **Undo** puts the names back. It is tried once (the flag is set after the attempt, so a start never nags); the command **Rename task notes to their titles** runs it again, and editing a todo's title renames that note anyway. The id lookup is rebuilt without ever emptying it (`Repository.reindex` swaps a finished rebuild in, and what happened meanwhile wins), because panels render while it runs.

## Performance

The panel redraws often, so reading must be cheap. `Repository.properties` keeps the parsed properties of each task note, keyed by path and valid while the file's modified time and size are unchanged; the plugin's own writes and the modify, rename and delete events drop an entry, and a note open in the editor is read from the editor each time (its unsaved text is newer than the disk). Autosave modify events of the note being typed in are coalesced by `refreshSoon` (400 ms trailing), while explicit actions still redraw at once. Bulk reads (the id lookup, `list`, the first reference index) go through `inBatches`, sixteen at a time and in order.

## Retiring tasks

`retireTasks` (service) applies the Retire window's choices; the pure rules (which tasks, allowed combinations, readable names, stripping properties) are in `src/retire.ts`. Task notes are found by the id in their frontmatter; notes that are already named after their title are not renamed by Retire, only notes still named after the id are, and only after their todos are about to lose their ids in the same step: per task the note is renamed, its todos are rewritten (plain text or a link generated from the renamed file), its properties stripped and the note trashed last. A task that fails at any step has its name restored and is reported while the others go on. Names are unique case-insensitively (`Plan`, `plan 2`, ...), avoid reserved Windows names and trailing dots, and are capped at 100 characters. Only Organized's own properties (derived from the task model) are removed; others stay, and the properties block goes only when nothing is left. Before writing, the old text of every note that will change and the planned renames are saved to `note-backups/retire-<time>.json` (the three newest are kept); a failed backup changes nothing. Undo reverses the content changes and then the renames; a run that trashes notes offers no Undo because it would relink todos to trashed notes.
